## Verification log — Phase 10: Testing & Deployment Prep (2026-11-11)

**In-memory MongoDB outcome:** `mongodb-memory-server`'s own binary downloader timed out in this sandbox (60s per attempt against fastdl.mongodb.org), but the official MongoDB 7.0.24 tarball was fetched directly with curl in ~4s; its `mongod` (ubuntu2204 build) runs correctly in this environment. Two environment traps were found and solved honestly: (a) `/tmp` is a 512MB tmpfs — WiredTiger's default cache preallocation died with `No space left on device`, fixed by keeping the binary + data under `~/workspace`; (b) the harness connects Mongoose's DEFAULT connection to the in-memory URI, so the real Express app (`src/app.ts`) runs unmodified against a real MongoDB. Verified by a smoke test: insert/find round-trip, unique-index enforcement (11000), and the expected transaction error on standalone mongod.

**Test framework:** Vitest 2 + Supertest 7 + mongodb-memory-server 10 (`backend/tests/`, `npm test`). **58 tests, all passing** (9 files): unit logic 12, payment-provider honesty 3, auth 9, permissions/RBAC 9, academics 6, finance 10, other modules 6, audit stripping 2, §36 end-to-end scenario (steps 1–19 as ONE sequential test) 1. No-DB probe regression: `backend/scripts/probe-no-db.mjs` — 8/8 pass. Both production builds re-run clean after all fixes (frontend 1,877+ modules).

**Transaction path:** standalone in-memory mongod does NOT support multi-document transactions (verified: "Transaction numbers are only allowed on a replica set member or mongos"), so the admission→enrollment conversion exercised its documented **sequential fallback** — and passed end-to-end (student + ADM number + verified parent link + active enrollment + guardian login). The transactional path itself can only be exercised on Atlas/a replica set.

**⚠️ In-memory caveat:** in-memory MongoDB validates logic against real MongoDB semantics, but it is NOT a substitute for the school's Atlas production environment (replica-set transactions, network latency, Atlas-specific behaviour, and load are not covered).

**Bugs found by the tests and fixed (Phase 10):**
| # | Bug | Evidence | Fix |
|---|---|---|---|
| 1 | **Refresh-token rotation could silently re-issue the SAME token.** `signRefreshToken` signed only `{sub, type}`; JWT `iat` has 1-second resolution, so two tokens issued for a user within one second were byte-identical and the "old" token still matched the stored hash. | Auth test "refresh ROTATES the refresh token" failed: new cookie === old cookie | `src/utils/tokens.ts` — every refresh token now carries a unique `jti` (`crypto.randomUUID()`). | 2 | **One login account could front MULTIPLE student records.** `Student.user` was a plain index; every "own record" resolver (portal, academic scope, finance) uses `findOne({ user })`, so a second link made resolution arbitrary. | Academics test "one login account fronts exactly ONE student record" got 201 instead of 409 | `student.model.ts` — `user` is now `unique + sparse`; `student.service.ts` — create/update pre-check returns 409 `USER_ALREADY_LINKED` (index is the backstop, matching the codebase pattern) |
| 3 | **Published report cards 404'd for EVERYONE** (`MARKS_NOT_FOUND`). `computeReportCard` populated the enrollment's class/section, then passed the populated OBJECTS into the schedule query and `String()`-compared a section object (`"[object Object]"`) — schedules never matched. Would have broken report cards in production too; the no-DB probes of earlier phases could never reach this code. | Academics test + a DB trace: publish 200, then report card 404 `MARKS_NOT_FOUND` for student AND admin | `exam.service.ts` — raw ids are extracted from the populated enrollment before querying/comparing (schedules lookup + class-position block).
